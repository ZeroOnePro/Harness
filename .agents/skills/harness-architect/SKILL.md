# 설계 경계와 대안 검토

요청 범위에서 구조를 선택할 근거를 만든다. 검토 요청이면 결과를 보고하고, 구현 요청이면 선택한 설계로 구현·검증까지 진행한다.

## 현재 구조를 근거로 판단

- 관련 진입점, 호출자, 데이터·상태 소유자, 외부 인터페이스, 기존 검사와 설계 결정을 먼저 찾는다. 파일명만으로 책임을 추정하지 않는다.
- 바뀌는 동작과 보존할 계약을 구분한다. 컴포넌트라면 표시·상태·도메인 로직의 책임을, 문서 하네스라면 시작 지침·상세 절차·원본 보관의 책임을 확인한다.
- 실제 파일·심볼·호출 경로를 근거로 문제를 기록한다. 긴 파일이나 비슷한 이름만으로 분리를 제안하지 않는다.

## 선택이 중요한 부분만 비교

- 복잡한 변경은 기존 구조의 최소 수정안과 책임 배치가 다른 대안을 비교한다. 이미 결정된 사소한 선택에 형식적인 대안을 만들지 않는다.
- 각 안의 인터페이스와 호출 예시를 짧게 그린다. 데이터 흐름, 의존 방향, 변경되는 호출자, 검증 경로를 포함한다. 검토만을 위한 미구현 코드를 실행 경로에 추가하지 않는다.
- 책임·상태의 소유자가 명확한가, 호출자가 내부 규칙을 알아야 하는가, 같은 정책을 여러 곳에서 수정해야 하는가, 순환 의존이나 불필요한 계층이 생기는가를 비교한다.
- 변경 파일·호환성·마이그레이션·검증 비용과 되돌릴 방법을 고려해 요청을 충족하는 안을 선택한다. 계층 수나 코드 줄 수만으로 우열을 정하지 않는다.

## 결정과 실행

- 결과는 문제와 근거, 대안별 절충, 선택 이유, 영향 범위, 확인 방법으로 충분하다. 지속적인 결정만 기존 설계 기록에 남긴다.
- 사용자 판단이 결과·범위·권한을 크게 바꾸는 경우에만 질문한다. 이미 위임된 되돌릴 수 있는 설계 선택은 진행한다.
- 구현 중 같은 우회나 계약 위반이 반복되면 새 근거로 설계를 다시 검토한다. 무관한 리팩터링으로 범위를 넓히지 않는다.
- 별도 모델·에이전트·다른 스킬 설치 없이 단일 에이전트로 수행할 수 있다. 위임이 필요하면 현재 세션에서 허용된 범위를 따른다.
