# 하네스 지침 적용 가이드 — Codex / Claude Code

작성일: 2026-09-17

이 문서는 함께 제공된 `AGENT_HARNESS_GUIDE.md`를 어디에 배치하고, 어떤 내용을 상시 지침·프로젝트 자료·검증 장치로 나눌지 설명한다. 모델·도구 갱신 때 재작업을 예약하고 검토하는 방법도 포함한다. 아래 폴더 구조와 운영 방식은 적용 제안이며, 실제 설치나 설정 변경을 완료했다는 뜻은 아니다.

## 1. 가장 간단하게 시작하기

1. 사용할 프로젝트의 루트에 `AGENT_HARNESS_GUIDE.md`를 저장한다.
2. 같은 위치의 `AGENTS.md`에 4절의 짧은 공통 지침을 추가한다. 기존 파일이 있으면 필요한 부분만 합친다.
3. Claude Code도 사용한다면 `CLAUDE.md`에서 공통 지침을 연결한다. 방법은 5절에 있다.
4. 프로젝트의 실제 실행·검증 방법을 추가하고 새 세션에서 적용 여부를 확인한다.
5. 진행 기록, 평가 기준, 자동 검사는 필요한 작업이 생겼을 때 단계적으로 추가한다.

전체 상세 가이드를 AGENTS.md와 CLAUDE.md에 각각 복사할 필요는 없다. 짧은 핵심 규칙과 상세 문서의 읽기 조건을 연결한다.

## 2. 무엇을 어디에 둘까?

| 내용 | 권장 위치 | 역할 |
| --- | --- | --- |
| 모든 프로젝트에 공통인 말투·질문 방식·업무 선호 | 사용자 전역 지침 | 짧은 요청 해석, 필요한 질문만 하기, 간결한 보고 |
| 프로젝트 목적·제약·실행 명령·문서 위치 | 프로젝트 AGENTS.md / CLAUDE.md | 이 프로젝트에서 항상 알아야 할 사실 |
| 여섯 축, 누락 정보 처리, 전문가 팁의 상세 설명 | 프로젝트 루트의 AGENT_HARNESS_GUIDE.md | 관련 작업에서 필요한 절만 읽는 참고 문서 |
| 시스템 구조·용어·중요한 과거 결정 | 기존 설계 문서 또는 docs/PROJECT_CONTEXT.md | 맥락을 추측하지 않게 하는 근거 |
| 테스트 명령·성공 기준·좋은 결과 예시 | 기존 테스트 문서 또는 docs/VERIFICATION.md | 완료 여부를 판단하는 기준 |
| 여러 세션에 걸친 진행 상태 | docs/agent-work/PROGRESS.md | 완료·미해결·다음 행동을 이어받는 기록 |
| 반복되는 평가 사례 | tests/ 또는 별도 평가 사례 파일 | 지침 변경이 동작을 개선했는지 비교 |
| 반드시 통과해야 할 검사 | 프로젝트 테스트·스크립트·CI | 말로 적힌 규칙을 실제 실행 결과로 확인 |

`docs/` 아래 파일명은 이 가이드의 제안이다. 이미 같은 역할의 문서가 있으면 그대로 사용하고 경로만 연결한다. 자동으로 읽힌다고 가정하지 말고 진입 지침에 읽는 조건을 적는다.

## 3. 도구별 기본 적용 위치

### Codex

- 개인 공통 지침: 기본적으로 `~/.codex/AGENTS.md`. `CODEX_HOME`을 설정한 환경은 해당 디렉터리를 기준으로 한다.
- 프로젝트 지침: 프로젝트 루트의 `AGENTS.md`.
- 같은 디렉터리에 `AGENTS.override.md`가 있으면 해당 파일이 우선 선택되므로, 수정한 지침이 적용되지 않을 때 확인한다.
- 하위 디렉터리 지침의 탐색 범위는 시작한 작업 디렉터리에 영향을 받는다. 실제 작업 위치에서 어떤 지침을 읽었는지 확인한다.

공식 근거: [Codex의 AGENTS.md 구성](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

### Claude Code

- 개인 공통 지침: `~/.claude/CLAUDE.md`.
- 프로젝트 지침: 프로젝트 루트의 `CLAUDE.md` 또는 `.claude/CLAUDE.md`.
- 공통 AGENTS.md를 사용하려면 CLAUDE.md에서 `@AGENTS.md`로 가져올 수 있다.
- 추가 규칙을 `.claude/rules/`에 둘 수 있다. 경로 조건이 없는 규칙은 시작 시 로드되므로 긴 참고 문서를 무조건 이 디렉터리에 넣지 않는다.

공식 근거: [Claude Code의 메모리와 지침 파일](https://code.claude.com/docs/en/memory).

### Windows에서의 경로

네이티브 Windows에서 홈이 `C:\Users\sungmin`인 환경이라면 기본 사용자 지침 경로는 다음과 같다.

```text
Codex:       C:\Users\sungmin\.codex\AGENTS.md
Claude Code: C:\Users\sungmin\.claude\CLAUDE.md
```

WSL·원격 서버·클라우드에서 실행한다면 그 실행 환경의 홈과 프로젝트를 기준으로 설정한다. 로컬 PC의 파일을 수정했다고 다른 환경에도 적용됐다고 가정하지 않는다.

## 4. AGENTS.md에 추가할 공통 지침

다음 블록은 프로젝트 루트에 상세 가이드가 있다는 전제의 적용 예시다. 경로를 바꿨다면 문구도 바꾼다.

```md
## 에이전트 작업 원칙

- 짧거나 불완전한 요청은 대화와 관련 자료를 근거로
  목표·산출물·제약·완료 기준으로 구체화한다.
- 실행 요청이면 설명에 머물지 않고 작업과 검증까지 진행한다.
- 질문 전에 필요한 정보가 대화·기존 문서·코드에 있는지 확인한다.
- 중요한 누락만 이유와 추천안을 붙여 질문한다.
  되돌리기 쉬운 사소한 선택은 스스로 결정한다.
- 필수 답변을 기다리는 동안 독립적인 작업은 계속한다.
  사실·대상·권한을 임의로 만들어 진행하지 않는다.
- 완료는 실제 결과로 확인한다. 부분 완료와 검증 한계를 숨기지 않는다.
- 토큰 절약을 이유로 필요한 맥락 확인이나 검증을 생략하지 않는다.

## 상세 지침을 읽는 조건

- 모호한 요청·필수 정보 누락: AGENT_HARNESS_GUIDE.md의 2~4절.
- 실행 실패·완료 검증: 5~6절.
- 긴 작업·세션 인수인계·반복 실수: 7~9절 및 11.4절.
- 성능·품질 최적화: 11.1절.
- 코드 동작 변경·버그 수정: 11.2~11.3절.
- 도구 연동·반복 자동화: 11.5절.
- 주관적 품질 평가·하네스 변경: 11.6절 및 12절.
- 관련 절만 읽고, 충분한 정보가 있으면 실행으로 넘어간다.
```

프로젝트에 맞는 사실도 짧게 덧붙인다. 아래 항목은 실제 값으로 채운다. 알 수 없는 항목을 가상의 명령이나 기준으로 확정하지 않는다.

```text
프로젝트 목적:
주요 실행 위치:
설계·용어·결정 문서 경로:
기본 실행 명령:
관련 테스트 또는 검증 명령:
수정하면 안 되는 대상과 이유:
대표적인 완료 기준:
```

이 항목을 전부 사용자가 작성할 필요는 없다. 에이전트가 기존 자료에서 먼저 채우고, 결과를 좌우하는 미확정 항목만 질문하도록 한다.

## 5. CLAUDE.md의 중복을 줄이는 방법

프로젝트 공통 원칙을 AGENTS.md 한 곳에서 관리한다면 프로젝트 루트의 CLAUDE.md에 다음을 추가한다.

```md
@AGENTS.md

## Claude Code에만 해당하는 사항
- 이 프로젝트에 실제로 필요한 도구별 차이만 여기에 기록한다.
```

기존 CLAUDE.md에 중요한 지침이 있으면 보존하고 공통 부분만 통합한다. 이 예시의 가져오기 문법은 Claude Code용이다. Codex에도 같은 문법이 통한다고 가정하지 않는다. 위 문법의 근거는 [Claude Code 공식 문서](https://code.claude.com/docs/en/memory)다.

상세 가이드 전체를 `@AGENT_HARNESS_GUIDE.md`로 가져오면 매번 큰 내용을 포함할 수 있으므로, 여기서는 짧은 AGENTS.md를 연결하고 상세 절은 필요할 때 읽도록 권한다.

## 7. 권장 폴더 구성

```text
프로젝트/
├─ AGENTS.md                     # 짧은 공통 지침과 실제 프로젝트 정보
├─ CLAUDE.md                     # 공통 지침 연결과 Claude 전용 차이
├─ AGENT_HARNESS_GUIDE.md         # 상세 운영 지침: 필요한 절만 읽기
├─ HARNESS_SETUP_GUIDE.md         # 이 적용 안내서: 사람의 설정·관리용
├─ docs/                         # 아래 문서는 필요할 때만 추가
│  ├─ PROJECT_CONTEXT.md         # 구조·용어·주요 결정
│  ├─ VERIFICATION.md            # 검증 방법·성공 기준·예시
│  └─ agent-work/
│     └─ PROGRESS.md             # 여러 세션에 걸친 진행 상태
├─ tests/                        # 실제 기능 검사·회귀 테스트
└─ scripts/                      # 프로젝트에 맞는 검사·측정 도구
```

작은 프로젝트는 위 네 개의 루트 문서만으로 시작할 수 있다. 단순 작업에는 진행 기록 파일도 생략한다. 기존 README, 설계 문서, 테스트 구조가 있으면 새 파일 대신 해당 자료를 연결한다.

## 8. 문서로 적을 것과 실제로 구현할 것

| 문서에 적을 원칙 | 실제로 필요한 장치 |
| --- | --- |
| 테스트 후 완료 보고 | 실행 가능한 테스트 명령과 결과 확인 |
| 변경 범위를 제한 | 도구 입력 검사, 작업 디렉터리, 필요한 권한 설정 |
| 실패하면 복구 | 변경 추적·백업·복구 가능한 작업 단위 |
| 반복 개선 | 측정 도구, 기준값, 결과 기록, 중단 조건 |
| 세션을 이어서 작업 | 저장된 상태와 다음 세션의 읽기 절차 |
| 같은 실수를 반복하지 않기 | 재현 사례와 회귀 검사 |

공통 검사는 프로젝트의 스크립트와 CI에 두면 여러 도구에서 재사용하기 쉽다. Claude Code에서 도구 이벤트에 맞춰 검사를 연결하려면 프로젝트 `.claude/settings.json`의 hooks 구성을 사용할 수 있다. 구체 설정은 실제 셸·명령·이벤트를 확인한 뒤 작성한다. [Claude Code hooks 공식 문서](https://code.claude.com/docs/en/hooks)

Claude의 hooks 설정을 Codex에 그대로 복사하지 않는다. 먼저 공통 검사 명령을 만들고 도구별 지원 방식에 맞춰 연결한다. 이 안내서에는 설치되거나 실행된 hook·CI·자동 복구 장치가 포함돼 있지 않다.

## 9. 적용 확인 방법

새 세션에서 다음 요청으로 파일 연결을 확인한다.

```text
현재 실제로 읽은 지침 파일의 경로를 알려줘.
추측하지 말고, 공통 하네스 규칙과 상세 가이드가 어떻게 연결되는지 확인해줘.
부족한 필수 정보가 생겼을 때 언제 질문하고 언제 스스로 진행할지도 짧게 설명해줘.
```

그다음 안전한 작은 작업으로 행동을 확인한다.

1. 형식 같은 사소한 정보를 생략했을 때 기존 관례로 진행하는가?
2. 결과가 크게 달라지는 필수 정보가 없을 때 정확한 질문을 하는가?
3. 이미 자료에 있는 내용을 다시 묻지 않는가?
4. 작업 후 실제 산출물·동작을 확인하는가?
5. 실제 외부 발송은 하지 않는 모의 사례에서, 수신자가 빠졌을 때 발송을 보류하는가?

지침을 읽었다는 답만으로 적용을 확정하지 않는다. 실제 행동을 함께 확인한다.

## 10. 기존 토큰 절약 지침과 합치는 순서

1. 기존 AGENTS.md·CLAUDE.md의 프로젝트 고유 정보는 보존한다.
2. 토큰 절약 규칙에서 이미 같은 내용이 있으면 중복을 제거한다.
3. 최소 탐색은 “정확한 판단에 필요한 정보가 확보될 때까지”로 해석한다.
4. 최소 테스트는 “변경 위험에 맞는 의미 있는 검증”으로 해석한다.
5. 질문 최소화와 필수 확인이 충돌하면, 결과·대상·권한을 좌우하는 정보는 확인한다.
6. 불필요한 질문·반복 실패가 생겼을 때만 규칙과 사례를 보완한다.

`AI_Coding_Agent_Token_Efficiency_Guide.md`를 이미 받았다면 비용 최적화 참고 자료로 함께 보관할 수 있다. 최신 하네스 가이드에는 토큰 절약 외에 의도 파악·정보 요청·검증·개선 원칙이 추가돼 있다.

## 11. 갱신 시점에 재작업 예약하기

하네스는 모델·도구 변화에 따라 다시 평가해야 한다. 기본값은 6개월마다 검토하는 정기 예약이며, 모델을 교체하거나 주요 도구가 바뀐 날에는 다음 예약을 기다리지 않고 임시 검토를 실행한다. 모델 출시를 자동 감지하지 못하는 환경에서는 출시 알림을 전제로 한 자동화를 만들지 말고, 정기 예약과 수동 앞당김을 함께 사용한다.

예약 작업의 설명에는 다음 범위를 명시한다.

```text
AGENTS.md·CLAUDE.md·skills·hooks·도구 설정과 대표 평가 사례를 검토한다.
대표 요청 5~10개와 과거 실패 사례를 같은 조건에서 실행한다.
하네스 요소를 한 번에 하나만 제거하거나 변경하고 결과를 비교한다.
효과 없는 규칙은 삭제 후보로 기록하고, 반복 실패를 막는 최소 요소만 유지한다.
변경한 파일, 검증 결과, 되돌림 방법, 다음 갱신일을 기록한다.
파일 수정·배포·메일 발송은 별도 권한과 요청이 있을 때만 수행한다.
```

예약은 검토를 시작하는 신호다. 예약이 실행됐다는 이유만으로 실제 하네스가 자동 수정됐다고 간주하지 않는다. 자동 수정을 원하면 그 범위와 대상 프로젝트를 별도로 명시해야 한다.

| 시점 | 작업 |
| --- | --- |
| 6개월마다 | 전체 하네스 검토와 대표 사례 재평가 |
| 모델 변경일 | 기존 지침·도구·평가의 임시 재평가 |
| 같은 실패가 2회 이상 반복될 때 | 원인에 맞는 최소 규칙·도구·회귀 사례 추가 |
| 규칙이 누적되어 충돌하거나 길어질 때 | 중복 규칙 제거와 상세 문서로의 이동 |
